Restore ip-pin as the default HA-cluster resume strategy on macOS Docker Desktop by fixing the IPAM feasibility probe at `pkg/internal/doctor/ipamprobe.go`. Today the probe's `{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}` template silently concatenates all attached-network IPs, the result fails `net.ParseIP`, and the probe falls through to `VerdictCertRegen` with the bogus reason `inspect returned invalid IP "invalid IP"` — routing every HA cluster on the regressing host to the (also-broken-until-Phase-57.3) cert-regen path.

The fix is staged behind a live diagnostic forensic capture (Task 1) that locks the final fix shape per CONTEXT.md stop-rule. The expected shape — centralized in a single `inspectProbeIP` helper — is: (a) replace both inspect templates with `{{(index .NetworkSettings.Networks "<probeNet>").IPAddress}}` to ask for the specific probe network's IP, (b) switch container start to `--network=none` + explicit `docker network connect <probeNet>` to eliminate multi-network attachment as a variable, (c) prefix the ParseIP-reject reason with `⚠️ ... likely a regression ... please file an issue` so future regressions surface immediately in user output, (d) surface the ip-pin verdict at create time on both docker and podman provider paths (parallel to the existing cert-regen Warnf), (e) cover the new behavior with a RED→GREEN unit test + a TestProvisionLogsInfoOnIPPin provider test, and (f) run a 4-env live UAT matrix (macOS DD, Linux Docker, macOS nerdctl, macOS podman) closing the bug-of-record on macOS DD and unblocking Phase 58.

Purpose: Phase 52 selected ip-pin as the preferred HA resume strategy (k3d precedent). The current regression silently demotes every HA cluster to cert-regen on the developer's primary test host. Without this fix, Phase 58 cannot close (test_09 fails through the broken cert-regen recovery path even after Phase 57.3 lands, because no Phase 58 cluster reaches the ip-pin path).
