# Phase 57.4: IPAM probe regression — Context

**Gathered:** 2026-05-18
**Status:** Ready for planning

<domain>
## Phase Boundary

Fix `pkg/internal/doctor/ipamprobe.go` so the IPAM feasibility probe correctly returns `VerdictIPPinned` on stock macOS Docker Desktop instead of silently falling back to `VerdictCertRegen` with the bogus `inspect returned invalid IP "invalid IP"` reason string. Restore ip-pin as the default strategy for HA clusters on healthy hosts.

The cert-regen path itself, the doctor-check registry shape, and the create-time strategy-selection logic are NOT in scope (those are Phase 57.3 / Phase 52 territory).

</domain>

<decisions>
## Implementation Decisions

### Investigation order (Task 1 = live diagnostic)

- Plan 01 **starts with a live diagnostic** against the failing host BEFORE any code changes. The literal `"invalid IP"` string (with a space) reaching `net.ParseIP` is suspicious enough that we need the actual `docker inspect` output before locking the fix shape.
- Diagnostic capture must include all four:
  - **Raw inspect output (all formats)** — `docker inspect <probe>` with no `--format`, with the current template `'{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'`, AND with `'{{json .NetworkSettings.Networks}}'`. See the full network state, not just what the current template extracts.
  - **Network attachments inventory** — `docker network ls`, `docker inspect <probeNet>`, and `Containers` section of `docker network inspect` to confirm whether multi-network attachment is the trigger.
  - **Docker Desktop version + kernel** — `docker version`, `docker info`, host kernel/build. The regression appeared between Phase 52 UAT (worked 2026-05-10) and 2026-05-16; we need to know if a DD update is implicated.
  - **Repro across networks** — Run the probe against the scratch network AND default `bridge` AND `kind`. Tells us if the bug is probe-network-specific or universal.
- Diagnostic output lives at `.planning/phases/57.4-ipam-probe-regression/uat-logs/57.4-01-ipam-probe-diag.txt` (plan-bundled forensic file, mirrors Phase 57.3 pattern).
- **Diagnostic drives fix shape:** if multi-network concatenation is confirmed → the index-by-network-name template (below) wins. If the IP is genuinely missing or DD returns the literal string for another reason → escalate to the architectural alternative (drop IP-capture, use `network connect --ip` dry-run as the feasibility test). Lock the final fix shape AFTER diagnostic.

### Fix shape (target — pending diagnostic confirmation)

- **Template:** `docker inspect --format '{{(index .NetworkSettings.Networks "<probeNet>").IPAddress}}' <probe>`. Asks for the specific network's IP we just attached. Robust against multi-network attachments and matches the probe's actual semantic intent.
- **Both call sites in `ipamprobe.go`** (pre-stop inspect at line 117, post-start re-inspect at line 155) get the fix together, via a small helper:
  ```
  inspectProbeIP(binary, probeName, netName string) (string, error)
  ```
  Parsing logic lives in exactly one place.
- **Other call sites:** researcher does `grep -rn 'NetworkSettings.Networks' --include='*.go'` and lists every call site in RESEARCH.md. Comment at `ipamprobe.go:115` references `realInspectState` — worth checking. If any other call site has the same bug shape, fix all of them atomically in Plan 01.
- **Network isolation for the probe:** switch step 2 (`docker run -d ... --network <probeNet> ...`) to `--network=none`, then `docker network connect <probeNet> <probe>` as a separate step. Eliminates multi-network attachment as a variable regardless of Docker Desktop's run-flag semantics.

### Failure-mode policy

- **Soft-fallback preserved, but loud:** when `net.ParseIP` rejects the captured value (currently `ipamprobe.go:129`), the verdict stays `VerdictCertRegen` (don't fail cluster creates over a probe bug) — BUT prefix the warn message with `⚠️ IPAM probe returned unparseable IP "%s" — this is likely a regression; please file an issue`. Future regressions become obvious in user output, not buried in a normal warn line.
- **Probe verdict surfaced at create-time:** `kinder create cluster --config <ha.yaml>` prints the probe verdict + reason on stdout for ALL verdicts (including `ip-pinned`), not just the non-default ones. Today ip-pin is silent; users can't tell which strategy their cluster is on without inspecting labels. The current cert-regen line stays; an analogous "HA cluster will use ip-pin resume strategy" line is added for the success path.
- **No CI gate** for the probe — GitHub Actions runs Linux Docker, which never reproduced the macOS DD bug-of-record. Unit tests + the live UAT script (below) are the right shape. Don't add CI noise that wouldn't have caught this class of bug.
- **No persistent probe log file** — stdout/stderr only. Users can `2>&1 | tee probe.log` if they want persistence. Don't introduce host filesystem responsibilities to a lightweight check.

### Plan structure & live UAT

- **Single plan** (`57.4-01-PLAN.md`) with sequential tasks:
  1. Live diagnostic forensic capture → `uat-logs/57.4-01-ipam-probe-diag.txt`
  2. RED unit test from the captured-verbatim failing fixture
  3. GREEN fix: `inspectProbeIP` helper extraction, `--network=none` + explicit `network connect`, index-by-name template
  4. Grep audit of other `NetworkSettings.Networks` call sites; fix any with the same bug shape (atomic)
  5. Loud-log refinement on the `ParseIP`-reject path
  6. Verdict surfacing in `kinder create cluster` HA path
  7. Live UAT script `hack/uat-57.4-ipam-probe.sh` + 4-env matrix run
- **Live UAT script** is dedicated (`hack/uat-57.4-ipam-probe.sh`). Asserts `./bin/kinder doctor ipam-probe` returns `verdict=ip-pinned` on a healthy host. End-to-end check: `./bin/kinder create cluster --config ha.yaml` then verify `io.x-k8s.kinder.resume-strategy=ip-pin` label on cp1. Owns its own evidence file under `uat-logs/`.
- **UAT environment matrix** (4 envs):
  - macOS Docker Desktop (the regressing env — closes the bug-of-record)
  - Linux Docker (sanity baseline — confirms fix doesn't break the path that always worked)
  - macOS with nerdctl (`VerdictUnsupported` short-circuit must still trigger)
  - macOS with podman (podman path must remain healthy after the fix)
- **Bug-of-record close gate** for unblocking Phase 58:
  1. 57.4 UAT passes on macOS DD with `verdict=ip-pinned`.
  2. Delete the left-up `uat-58-01` cluster (created on cert-regen strategy; label is permanent — wrong gate for validating ip-pin).
  3. Re-run `hack/uat-47-ha-smoke.sh` on a FRESH HA cluster, which now routes via ip-pin. test_09 closes Phase 58.
