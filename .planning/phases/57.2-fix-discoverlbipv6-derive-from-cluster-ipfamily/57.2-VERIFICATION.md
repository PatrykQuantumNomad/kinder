The phase goal — "`kinder resume` on a vanilla IPv4 HA cluster renders the LB listener at `address: "0.0.0.0"` so host kubectl reaches the apiserver after resume on macOS Docker Desktop" — is achieved end-to-end:

1. **Architecturally:** `discoverLBIPv6` (the docker-network-EnableIPv6 probe that mis-classified IPv4 clusters on macOS Docker Desktop's dual-stack kind network) is **deleted entirely** from the codebase. Replacement: `loadbalancer.ClusterIPFamily()` reads the `io.x-k8s.kinder.ip-family` label stamped at create time on every cluster container by all 3 providers. Single source of truth: create-time and resume-time agree by construction.

2. **At the listener template:** IPv4 clusters render `address: "0.0.0.0"`; IPv6/dual clusters render `address: "::"` + `ipv4_compat: true` (the dual-stack idiom for macOS Docker Desktop compatibility). The conditional is correctly scoped via `{{- if .IPv6 }}`.

3. **In live UAT on the exact regression environment:** macOS Docker Desktop with IPv6 enabled + dual-stack `kind` network, the IPv4 cluster's post-resume `lds.yaml` shows `address: "0.0.0.0"` (byte-identical to pre-resume), host kubectl returns 5/5 nodes Ready, all 6 IPv4 containers carry `io.x-k8s.kinder.ip-family=ipv4`, and the IPv6 cluster's post-resume `lds.yaml` correctly shows `address: "::"` + `ipv4_compat: true`.

4. **In the test suite:** `go build ./...` clean; `go test -race -count=1` green on all 3 affected packages including the named regression test `TestClusterIPFamily_MacOSDualStackNetwork_IPv4Cluster` which asserts the new helper NEVER calls `docker network inspect`.

5. **Phase 58 unblocked:** The IPv4-resume-then-Ready path that Phase 58 UAT test_09 exercises is verified end-to-end on the regression environment by Phase 57.2 Plan 02 test_05. Phase 58 has no IPv6 HA UAT case, so the IPv6 cert-regen finding is correctly out of scope for SC6.
