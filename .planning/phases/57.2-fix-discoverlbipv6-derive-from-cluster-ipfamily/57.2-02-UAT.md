## SC4 Structural Caveat — macOS Docker Desktop port-mapping topology

Plan 02's SC4 originally read: *"On macOS Docker Desktop with IPv6 ENABLED, an explicit
IPv6 cluster passes `kubectl get nodes` from the host after pause/resume via the Docker
Desktop IPv4 port-mapping (verifies ipv4_compat actually lets the host kubectl reach an
IPv6 listener)."*

**This SC is structurally unreachable on macOS Docker Desktop** because Docker Desktop's
port-mapping topology mirrors the cluster's IPFamily, not both families:

- IPv4 cluster's LB exposes **only** `127.0.0.1:<port>->6443/tcp` (IPv4-only binding).
- IPv6 cluster's LB exposes **only** `[::1]:<port>->6443/tcp` (IPv6-only binding).

Live verification captured during forensic inspection:

```
$ docker ps --filter name=uat-572-ipv6-external-load-balancer --format '{{.Ports}}'
[::1]:64009->6443/tcp
```

There is no IPv4 port-mapping for an IPv6 cluster's LB to exercise `ipv4_compat: true`
from the host on macOS Docker Desktop. The `ipv4_compat: true` setting is architecturally
defensive — a connection arriving from inside the docker network on the IPv4 family
would still be accepted by the `::` listener — but it is not actively exercised by the
host kubectl path on this topology.

### Resolution

The listener-fix portion of SC4 **is** verified at file level (test_08 + test_10 confirm
`address: "::"` + `ipv4_compat: true` pre- and post-resume). The "host-via-IPv4" wording
of SC4 is documented as inapplicable on macOS Docker Desktop owing to the upstream
port-mapping topology. No SC4 wording revision is filed in this UAT document — that is
roadmap-author scope. Flagged here for the verifier (gsd-verifier) to record.

## Forensic Deep-Dive — IPv6 HA cluster cert-regen recovery finding

`test_11` failed with TLS EOF on host kubectl against the resumed IPv6 cluster. Live
diagnostics on the still-running `uat-572-ipv6` cluster isolated the root cause cleanly:
**the LB and its config are correct; the apiservers themselves are crash-looping because
they can't TLS-handshake to etcd on `[::1]:2379` after Phase 52's cert-regen flow.**

### Diagnostic sequence

```
$ docker exec uat-572-ipv6-control-plane sh -c 'curl -k --max-time 5 https://127.0.0.1:6443/healthz'
curl: (7) Failed to connect to 127.0.0.1 port 6443 after 0 ms: Could not connect to server
# → Apiserver on cp1 is NOT bound to 6443 (not listening).

$ docker exec uat-572-ipv6-worker sh -c 'curl -k --max-time 5 https://uat-572-ipv6-control-plane:6443/healthz'
curl: (7) Failed to connect to uat-572-ipv6-control-plane port 6443 after 0 ms: Could not connect to server
# DNS resolves to fc00:4d57:1afd:1f1b::a; apiserver not bound anywhere.

$ docker exec uat-572-ipv6-control-plane sh -c 'ps aux | grep -E "kube-apiserver|etcd"'
# etcd IS running on [::1]:2379 and [fc00:...:a]:2379.
# (kube-apiserver process not in list — crash looping.)

$ docker exec uat-572-ipv6-control-plane sh -c 'crictl logs --tail=20 <kube-apiserver-container>'
# Last 20 lines:
W ... grpc: addrConn.createTransport failed to connect to {Addr: "[::1]:2379" ...
  Err: connection error: desc = "transport: Error while dialing: dial tcp [::1]:2379:
  operation was canceled"
W ... transport: authentication handshake failed: context canceled
W ... transport: authentication handshake failed: context deadline exceeded
F ... Error creating leases: error creating storage factory: context deadline exceeded
# → kube-apiserver fatals out after ~20s of failing to handshake with etcd → crash loop.
```

### Root-cause statement

Phase 52's HA cert-regen flow (which regenerates etcd peer certs after IPAM drift
detection) leaves the apiserver→etcd client TLS connection broken on IPv6 HA clusters.
Either the regenerated `etcd/server.crt` doesn't include `[::1]` in its SAN list, or the
etcd cluster can't re-establish peer connections under the new certs and thus can't
service apiserver requests. Phase 52 was never UAT'd against an IPv6 HA cluster — the
IPv4 HA UAT in Phase 47 / Phase 58 was the only Phase 52 validation.

### Why this is NOT a Phase 57.2 issue

- Phase 57.2's listener fix is verified correct at file level for both IPv4 and IPv6
  `lds.yaml` (test_02, test_04, test_08, test_10 — all PASS).
- Phase 57.2's `cds.yaml` reapply is correct on both clusters (3 upstream backends listed
  on IPv4 per the cds snippet above; 3 upstream backends listed on IPv6 per the relevant
  section of `ipv6-diag.txt`).
- Phase 57.2's label injection works on every container kind (IPv4 test_06 PASS; IPv6 LB
  carries the label per `ipv6-diag.txt` line 11; the read side never fired on the IPv6
  cluster because the apiserver layer crashed before kubectl could reach it).
- The failing layer is the **apiserver→etcd handshake inside the CP container** —
  completely upstream of the LB and untouched by Phase 57.2's edits.

### Follow-up phase filing

Suggested new phase: **Phase 57.3 — IPv6 HA cluster cert-regen recovery** (alternatively
Phase 52.1 if the user wants it scoped under Phase 52's lineage).

**Goal:** After Phase 52's cert-regen fires on an IPv6 HA cluster, apiservers must
successfully TLS-handshake to etcd on `[::1]:2379` (or `[fc00:...]:2379`) and resume
serving traffic.

**Likely fix areas:**
- `etcd/server.crt` regeneration must include IPv6 loopback (`[::1]`) and link-local
  addresses in its SAN list.
- OR the etcd cluster peer re-coordination after cert-regen needs IPv6-aware retries.

**Reference evidence:**
- `.planning/phases/57.2-fix-discoverlbipv6-derive-from-cluster-ipfamily/uat-logs/ipv6-diag.txt`
  (live diagnostic capture, including LB labels + lds/cds contents + crictl pod listing).
- This UAT.md's "Forensic Deep-Dive" section (above).
- `.planning/phases/57.2-fix-discoverlbipv6-derive-from-cluster-ipfamily/uat-logs/ipv6-resume.log`
  + `ipv6-kubectl.log` (resume completion timing + TLS EOF transcript).
