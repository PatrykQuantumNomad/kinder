# Phase 57.2: Fix `discoverLBIPv6` — derive IPv6 mode from cluster IPFamily, not docker network EnableIPv6 - Context

**Gathered:** 2026-05-15
**Status:** Ready for planning

<domain>
## Phase Boundary

Replace `pkg/internal/lifecycle/lbreapply.go:59-90` (`discoverLBIPv6`) — currently probes `docker network inspect --format '{{.EnableIPv6}}'`, which is `true` on macOS Docker Desktop's `kind` network by default and therefore mis-classifies vanilla IPv4 clusters as IPv6 — with a cluster-authoritative IPFamily derivation. Resume-time and create-time must agree on the meaning of "IPv6" for the LB listener template.

In scope:
- Write-side: stamp an `io.x-k8s.kinder.ip-family` label on every cluster container at create time
- Read-side: resume reads the label; deletes the buggy `discoverLBIPv6`
- Listener template (`pkg/cluster/internal/loadbalancer/config.go:70`): add `ipv4_compat: true` to the IPv6/dual branch so dual-stack listeners on macOS Docker Desktop accept the host's IPv4 port-mapping connections
- Shared helper `clusterIPFamily(node) (bool, error)` consumed by both paths so divergence becomes architecturally impossible
- FakeNode test matrix including the exact bug-of-record (dual-stack docker network + IPv4 cluster label)
- Live IPv6 UAT inside Phase 57.2's plan (requires Docker Desktop IPv6 enabled)

Out of scope (deferred):
- Pre-57.2 cluster backward compatibility — no installed user base; users delete-and-recreate
- IPv6-only docker network creation logic in kind itself
- Consolidating other Phase 52 labels under a unified scheme

</domain>

<decisions>
## Implementation Decisions

### Fix-shape source

- **Primary shape: Option B (create-time label)** — write `io.x-k8s.kinder.ip-family={ipv4|ipv6|dual}` at create-time; read it at resume-time. Authoritative; no DNS/network heuristics.
- **Why Option A rejected:** Empirically broken on macOS Docker Desktop. The `kind` docker network is dual-stack by default (`EnableIPv6=true`), so every CP container has BOTH a populated `IPAddress` (172.19.0.X) and `GlobalIPv6Address` (fc00:f853:ccd:e793::X) regardless of the cluster's actual IPFamily. CP network inspection cannot distinguish IPv4-only cluster from dual-stack cluster — same bug shape as the function being fixed. Verified against the live forensic cluster `uat-58-01` 2026-05-13.
- **Why Option C rejected:** Path/format coupling on `/kind/kinder-cluster-config.yaml` (or wherever the spec is persisted) is fragile across kind versions.
- **Label scope:** All cluster containers (LB + CPs + workers). Uniform; useful for future diagnostic checks; matches Phase 52's container-labeling pattern.
- **No pre-57.2 fallback:** No installed user base. If the label is missing at resume, fail-loud with "delete and recreate the cluster" guidance. Direct quote: "we don't have any [pre-57.2 users] and the user can just delete the old cluster and create a new one." This simplifies the read-side significantly — no heuristic fallback path needed.
- **Signature:** Keep `bool` IPv6 — `WriteDynamicConfig(node, cps, ipv6 bool)` stays unchanged. Dual-stack collapses to `true`, matching the existing create-time semantics at `loadbalancer.go:70-71`.
- **Label key:** `io.x-k8s.kinder.ip-family` (kebab-case, mirrors Phase 52's `io.x-k8s.kinder.resume-strategy`).

### Dual-stack listener policy

- **Listener template fix is in scope for Phase 57.2.** The current template at `pkg/cluster/internal/loadbalancer/config.go:70` renders `address: "::"` for IPv6/dual modes; Envoy defaults `socket_address.ipv4_compat: false`, so the listener becomes IPv6-only. On macOS Docker Desktop the host's port-mapping is always IPv4 → can't reach an IPv6-only listener.
- **Template change:** Add `ipv4_compat: true` to the IPv6/dual branch. Single listener; native Envoy dual-stack idiom; minimal diff. IPv4-only mode stays `"0.0.0.0"`.
- **Resume matches (corrected) create-time exactly.** After Phase 57.2 lands, both paths render the same listener for the same cluster IPFamily.
- **Latent bug acknowledgment:** This was a pre-existing create-time bug masked by the fact that nobody had run macOS Docker Desktop with a dual-stack cluster + host kubectl. 57.2 closes both the resume regression AND the latent create-time bug atomically because they share the same template.

### Test strategy

- **Parity guarantee (architectural):** Both create-time and resume-time call a single shared helper `clusterIPFamily(node) (bool, error)`. One source of truth — they cannot disagree by construction. (Phase 57.1's separate `discoverLBIPv6` was the divergence vector.)
- **Mandatory regression test:** Named test `TestDiscoverLBIPv6_macOSDualStackNetwork_IPv4Cluster` (or equivalent) sets up: docker network with `EnableIPv6=true` + cluster containers labeled `ip-family=ipv4`. Asserts the function returns `false`. This is the bug-of-record from 2026-05-13.
- **FakeNode test matrix:** `{ipv4, ipv6, dual}` × `{macOS-style dual-stack network, linux-style IPv4-only network}` = 6 fixtures. All must produce the IPv6 flag value that matches the cluster label, NOT the network state.
- **Live IPv6 UAT inside Phase 57.2's plan** (not deferred to Phase 58). Plan includes a checkpoint task: developer creates an IPv6-explicit cluster with `networking.ipFamily: ipv6`, pause + resume, asserts `lds.yaml` renders `address: "::"` and host kubectl reaches the apiserver. Requires Docker Desktop IPv6 enabled (developer setup step in the plan).
- **Template grep assertion:** Unit test asserts `grep -q "ipv4_compat: true"` on rendered output for IPv6/dual fixtures; not for IPv4. Matches existing `config_test.go` style; lighter than golden snapshots.

### Create-time symmetry

- **Helper home:** `pkg/cluster/loadbalancer/` — Phase 57.1's non-internal bridge package. Colocated with `WriteDynamicConfig`. Both write-side (label stamping) and read-side (helper) live alongside the consumer.
- **Plan structure: single wave, atomic.** One plan covering: label writer at create-time + listener template fix + shared helper + resume read-side + legacy probe deletion + FakeNode matrix + live IPv6 UAT. Atomic landing means create and resume always agree at HEAD; no half-merged intermediate state.
- **Delete `discoverLBIPv6` entirely.** Single call site (resume.go); no installed user base needing fallback; no second consumer in the codebase. Carry-over deprecation comments would only accumulate technical debt.
- **Write site:** Stamp the `ip-family` label EARLIER in the create flow than Phase 52's IP-pin module. ip-family is a cluster-wide attribute — non-HA single-CP clusters should also be labeled. Phase 52's IP-pin module is HA-only and would miss single-CP clusters.

### Claude's Discretion

The following were explicitly "You decide"; recording so the planner sees the recommendations:

- **Fix-shape primary choice:** Option B (label). Driven by the empirical breakage of Option A on macOS Docker Desktop.
- **Signature form:** `bool` IPv6 (not an `IPFamily` enum). Consistency with existing `WriteDynamicConfig(..., ipv6 bool)`; dual collapses to `true`.
- **Label key naming:** `io.x-k8s.kinder.ip-family` kebab-case. Mirrors Phase 52.
- **Listener template form:** Add `ipv4_compat: true` to the IPv6/dual branch. Single-listener; native Envoy idiom.
- **Parity mechanism:** Shared helper (not parity-assertion test). Cheapest and strongest guarantee.
- **Template test form:** grep assertion on rendered output. Matches existing test style.
- **Helper home:** `pkg/cluster/loadbalancer/`. Colocated with `WriteDynamicConfig`.
- **Legacy probe handling:** Delete `discoverLBIPv6` entirely.
- **Label write site:** Earlier in create flow than Phase 52's IP-pin module. Cluster-wide attribute including single-CP clusters.
