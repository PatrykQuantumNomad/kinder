# Phase 57.3: HA cluster cert-regen recovery - Context

**Gathered:** 2026-05-16
**Status:** Ready for planning

<domain>
## Phase Boundary

Make Phase 52's `RegenerateEtcdPeerCertsWholesale` recovery path actually work end-to-end. After `kinder pause` + `kinder resume` forces the cert-regen strategy on any HA cluster (IPv4 / IPv6 / dual-stack), every `kube-apiserver` process must successfully complete its TLS handshake to its local etcd within its startup budget, and all CP nodes must reach Ready within `--wait 15m`.

**In scope:**
- Diagnostic capture from the live failing cluster (`uat-58-01`) before any code change
- Widening the cert-regen scope beyond `etcd-peer` (current) per evidence
- Replacing sleep-based gates with active health-polling for etcd
- Adding an explicit `kube-apiserver` static-pod cycle to force the apiserver to re-read regenerated client certs
- Diagnostic dump on hard-fail (keep `delete and recreate the cluster` semantic)
- New `--strategy=<auto|ip-pin|cert-regen>` flag on `kinder resume` (developer surface for forcing the recovery path; required by UAT)
- Bumping the cert-regen SC `--wait` budget to `15m`
- Net-new live UAT script `hack/uat-57.3-cert-regen.sh` covering IPv4, IPv6, dual-stack HA fixtures

**Out of scope (other phases):**
- Phase 57.4 — IPAM probe regression at `pkg/internal/doctor/ipamprobe.go:131` (sibling phase)
- Phase 52 redesign — cert-regen is the documented fallback, we are fixing it, not replacing it
- Phase 58 — live UAT closure for Phase 47 + 51 (runs after 57.3 + 57.4 land)

</domain>

<decisions>
## Implementation Decisions

### Diagnostic confirmation (gate before any code change)

- Plan 01 Task 0 is `diagnostic-capture` — runs against the still-up `uat-58-01` cluster (3-CP + 2-worker + 1-LB, IPv4, cert-regen strategy, all CPs missing `/kind/ipam-state.json`).
- Three diagnostics, captured in sequence on cp1:
  1. **Cert serial comparison** — `openssl x509 -noout -serial` on `/etc/kubernetes/pki/etcd/{server,peer}.crt` + `/etc/kubernetes/pki/apiserver-etcd-client.crt`. Hypothesis: only peer.crt serial changed; server.crt and apiserver-etcd-client.crt unchanged.
  2. **Manual etcdctl health-check** — from inside cp1: `etcdctl --cacert=/etc/kubernetes/pki/etcd/ca.crt --cert=/etc/kubernetes/pki/apiserver-etcd-client.crt --key=/etc/kubernetes/pki/apiserver-etcd-client.key endpoint health --endpoints=127.0.0.1:2379`. Confirms the cert-pair mismatch at the protocol level (not just by inspection).
  3. **SAN inspection** — `openssl x509 -text -in /etc/kubernetes/pki/etcd/server.crt`. Verify SANs include 127.0.0.1 / localhost / cp1-hostname. Catches a second possible cause (stale SAN list).
- **Stop-rule:** All three diagnostics must point at the same root cause (i.e. align) before locking the cert-set decision. If they diverge, the planner halts and surfaces the conflict.
- **Disposition:** Diagnostic outputs inline in `57.3-CONTEXT.md` `<specifics>` section (this file, post-capture) and in `57.3-RESEARCH.md`. NO separate `forensics/` directory. Unit tests use FakeNode/FakeCmd with synthetic cert data — not pinned to live captures.
- After Task 0 captures all three on `uat-58-01`, the planner runs `./bin/kinder delete cluster --name uat-58-01` before building fresh UAT fixtures.

### Cert scope of regen (evidence-driven; locked by Plan 01 Task 0)

- The exact cert set is **Claude's discretion** based on Task 0 diagnostic outputs. The planner derives the set from the serial-comparison + etcdctl-health diagnostics — only certs that diagnostics prove stale are regenerated.
- Anticipated minimal set if the narrow hypothesis holds: `etcd-peer` (current), `etcd-server`, `apiserver-etcd-client`, `etcd-healthcheck-client`. The planner does NOT preemptively widen to `kubeadm certs renew all` — narrow regen reduces blast radius.
- Per-CP flow uses **renew-then-cycle per cert type** (not batched renew + single cycle). Slower (~45s extra per cert type per CP) but safest if certs interact during kubelet pickup.
- Cross-CP order is **strictly sequential** CP1 → CP2 → CP3 (matches current `RegenerateEtcdPeerCertsWholesale` pattern). No parallelism — would risk simultaneous etcd downtime + quorum loss. No quorum-health gate between CPs (the per-cycle etcdctl health-poll on each CP is sufficient).
- Cycle target depends on which cert was renewed:
  - `etcd-peer`, `etcd-server`, `etcd-healthcheck-client` → cycle `/etc/kubernetes/manifests/etcd.yaml`
  - `apiserver-etcd-client` → cycle `/etc/kubernetes/manifests/kube-apiserver.yaml`
- **Post-pass verification per CP:** `kubeadm certs check-expiration` parsed to confirm all regenerated cert expirations moved forward. Hard-fail if any didn't.

### Recovery sequencing + failure semantics

- **Etcd ready-gate:** Replace the existing 20s static `staticPodRecreationWait` (`certregen.go:42`) with an active `etcdctl --cacert=... endpoint health --endpoints=127.0.0.1:2379` poll, every 1s up to 60s. Hard-fail if timeout. Faster on the happy path (etcd typically up in 3-5s) and catches the real failure instead of trusting a fixed sleep. The 25s pre-cycle sleep (`kubeletFileCheckFrequency + staticPodCycleSafetyMargin`) stays — it's gating kubelet's manifest-removal pickup, not etcd readiness.
- **Apiserver pickup:** kube-apiserver does NOT auto-reload `--etcd-certfile` / `--etcd-keyfile`. After regenerating `apiserver-etcd-client.crt`, the fix does an **explicit `kube-apiserver.yaml` mv-out/sleep/mv-in cycle** (symmetric with the etcd cycle). Followed by an apiserver-healthz poll (`curl -k --max-time 5 https://127.0.0.1:6443/healthz` from inside the CP container) every 1s up to 60s.
- **Failure path:** On any failure (kubeadm exit ≠ 0, etcdctl-health timeout, apiserver-healthz timeout, check-expiration mismatch) → **diagnostic dump THEN hard-fail** with the existing `Cluster state is undefined — delete and recreate the cluster` wording. Diagnostic dump uses `logger.Warnf`:
  - `etcdctl member list --write-out=table`
  - `kubeadm certs check-expiration`
  - last 20 lines of `crictl logs <kube-apiserver-container>`
  - serial-number table of all regenerated certs
- **Time budget:** Worst-case (4 cert types × 3 CPs × (25s + ~5s etcd-health + apiserver cycle ~30s) ≈ 12 min). Phase 57.3 SC1+SC2 use `--wait 15m`. Planner updates ROADMAP.md Phase 57.3 SCs accordingly and patches `hack/uat-47-ha-smoke.sh` test_09 `--wait 5m` → `--wait 15m` as a safety bump (test_09 itself may route through ip-pin post-57.4, but the budget is right-sized for the cert-regen path).

### `--strategy` flag on `kinder resume` (Phase 57.3 deliverable)

- **First-class developer flag**, not test-only: `kinder resume --strategy=<auto|ip-pin|cert-regen>`. Default `auto` preserves current behavior (probe + label dispatch). Explicit values bypass the dispatch logic and force the named path.
- Required because Phase 57.4 will fix the IPAM probe, restoring `ip-pin` as the default — meaning the cert-regen path can no longer be exercised by simply running `kinder resume` on any HA cluster. UAT MUST force `cert-regen` to verify the fix.
- Doubles as a future debug/recovery hook (e.g. operator override when ip-pin fails on a specific host).
- Flag validation: reject any value other than the three. Document in `kinder resume --help`.

### Live UAT (autonomous via gsd-executor; new dedicated script)

- New `hack/uat-57.3-cert-regen.sh` covering 3 fresh fixtures: vanilla IPv4 HA (3-CP + 2-worker + 1-LB), explicit IPv6 HA (`networking.ipFamily: ipv6`), dual-stack HA (`networking.ipFamily: dual`).
- Per fixture: `./bin/kinder create cluster --config <ha.yaml>` → `./bin/kinder pause` → `./bin/kinder resume --strategy=cert-regen --wait 15m` → assert apiserver healthz from inside cp1 + host `kubectl get nodes` returns all 5 Ready + cert serials post-resume differ from pre-resume capture for the renewed set.
- **Existing fixture `uat-58-01` is NOT reused** — it is deleted after Plan 01 Task 0 diagnostics complete (clean baseline; no left-up-cluster drift).
- **Execution mode:** Autonomous via gsd-executor. If autonomy fails on docker-exec / cluster operations (historical flakiness), fall back to the Phase 57.2-02 developer-driven UAT pattern — gsd-executor halts at the checkpoint, developer runs the script manually, captures evidence under `uat-logs/`, commits 57.3-02-UAT.md. The script itself is identical in both modes.
- The two Phase 58 UAT scripts (`hack/uat-47-ha-smoke.sh`, `hack/uat-57.2-ipv6-listener.sh`) are NOT extended for 57.3 — they remain ownership of Phase 58 / Phase 57.2 respectively; the `--wait 15m` bump on test_09 is the only edit.

### Claude's Discretion

- Exact cert set regenerated (locked by Plan 01 Task 0 diagnostics — see "Cert scope" above)
- Plan split between code/tests vs UAT (1 plan vs 2 plans) — planner's call based on commit-density and per-plan timing budgets

<specifics>
## Specific Ideas

- The bug-of-record cluster (`uat-58-01`) is still up on the host as of 2026-05-16 13:11 UTC. Plan 01 Task 0 captures the three diagnostics from it; then deletes it. Reference: `.planning/phases/58-live-uat-closure-for-phase-47-51/uat-logs/2026-05-16-uat-58-01-cert-regen-failure.txt` (88-line forensic snapshot, captured pre-discuss-phase).
- The fatal pattern is byte-identical to Phase 57.2's IPv6 finding (`.planning/phases/57.2-fix-discoverlbipv6-derive-from-cluster-ipfamily/uat-logs/ipv6-diag.txt`): `addrConn.createTransport failed to connect to {Addr: "127.0.0.1:2379"}` → `transport: authentication handshake failed: context deadline exceeded` → `F instance.go:233] Error creating leases: error creating storage factory: context deadline exceeded`. The IPv6 finding was scoped as IPv6-only at first; the IPv4 repro on `uat-58-01` proved otherwise.
- The current `certregen.go:131-167` implementation runs ONLY `kubeadm certs renew etcd-peer`. The etcd-peer cert is for etcd↔etcd communication on port 2380. The failure is apiserver→etcd on port 2379, which uses `etcd-server` (presented by etcd) + `apiserver-etcd-client` (presented by apiserver). Strong hypothesis: those two are stale post-rotation; diagnostics will confirm or deny.
- The W2-naming `RegenerateEtcdPeerCertsWholesale` function name is preserved (resume.go already calls it as an unqualified name from the same package, per `certregen.go:18-23`). Inside the function, the scope expansion is internal — no API rename needed.
- `pkg/internal/lifecycle/certregen.go:50` defines `certRegenSleeper` for test-time sleep injection. The new etcdctl-health-poll path needs a parallel injection point — likely `etcdHealthChecker = func(node nodes.Node) error { ... }` package-level var, swappable by tests for an instant-OK or instant-fail mock. Same pattern as `lbCmderState` from Phase 57.1.
- `--strategy` flag implementation: lives in `pkg/cmd/kind/resume/resume.go` (the cobra command entry point). The dispatch in `pkg/internal/lifecycle/resume.go` Resume() reads the strategy from a new field on the resume options struct.
- UAT script convention: shell pipefail + strings-marker freshness gate (Pitfall 23) at top, matching `hack/uat-47-ha-smoke.sh` and `hack/uat-57.2-ipv6-listener.sh`. Each test logs to a timestamped file under a per-fixture `uat-logs/` subdirectory.

</specifics>

## Deferred Ideas

- **Phase 57.4 — IPAM probe regression**: separately filed in ROADMAP.md. Either 57.3 or 57.4 can land first; both block Phase 58. The two are siblings; 57.3 fixes the broken recovery path, 57.4 unbreaks the upstream probe so the recovery path is exercised less often.

A future phase could explore alternatives — e.g., `kinder pause` capturing the cluster network state and `kinder resume` restoring it exactly so cert rotation is never needed. Out of scope for 57.3.

- **etcd member health gate before next CP**: dropped from Area 3 decisions (the per-cycle etcdctl health-poll is sufficient). If 57.3 UAT shows mid-pass quorum loss, file a follow-on phase to add the inter-CP gate.
- **Single-plan vs two-plan split**: planner's call. Phase 57.1 used two plans (helper + wire), 57.2 used two plans (code + UAT). Either pattern is acceptable here.
